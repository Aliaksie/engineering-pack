# Turn a feature into useful slices

Use the supplied feature intent, applicable project policy and current grounding/audit evidence.
Distinguish the actor's problem from a proposed screen, API or technical implementation.
Preserve explicit solution constraints; treat illustrative solutions as proposals rather than
inventing research or requirements to justify them.

Slice work around an independently useful outcome instead of separate UI, service and database
tasks. State the actor and desired result, then the observable acceptance conditions. Add a
boundary, dependency or verification note only when it prevents a consequential misunderstanding.
Avoid repeating the same requirement under several headings.

Carry confirmed requirements, assumptions and open choices distinctly. An assumed behavior
must remain conditional where it appears in the criteria. Ask about a decision that prevents a
usable story; continue unaffected slices with visible, bounded assumptions. Do not invent
architecture or dependencies from an unsupported implementation guess.

For interactive outcomes, consider the states and transitions the user actually encounters:
loading or pending work, empty results, errors, permissions and recovery where relevant.
Include meaningful accessibility, feedback/microcopy and responsive behavior when established
by the request or policy. Additional UX choices remain proposals until agreed, not hidden
acceptance requirements.

Reuse the shared evidence packet across drafts. Batch missing factual searches; an authorized
economical worker can extract cited facts from bounded inputs, while product scope and acceptance
judgment stay with the main reasoner. Refresh evidence affected by changed sources or scope.

Return local drafts or write to the requested location. Keep source specifications intact and
leave tracker publication or transitions to a separately authorized action. No particular
tracker, template system or UI stack is required.
