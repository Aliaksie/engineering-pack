# Make the next change executable

A useful plan lets another implementer start without repeating the investigation. Begin with
the requested outcome and identify the decisions that still affect behavior. Reuse accepted
plans and current evidence instead of producing a new plan merely because this skill was loaded.

Inspect applicable instructions, the relevant implementation and real check commands.
Use `craft-delivery-inspect-architecture` for an unresolved boundary. When work crosses
repositories, carry forward supplied ownership of facts, generation, dependencies, tests, CI
and outputs; inspect only unresolved responsibilities. A data-only consumer stays data-only
when a separate engine owns execution. Unknown ownership is a decision gap, not permission to
vendor that engine. Revisit ownership when later sources change scope; ordinary local work
needs no separate architecture stage.

For substantial work, identify the next unknown, independent evidence requests, dependencies,
execution owner and acceptance in the existing task record. Use bounded deterministic lookup
for known symbols, exact text and metadata; inspect coverage and truncation. Stage dependent
questions after their inputs. A permitted economical worker may interpret a narrow inventory;
keep ambiguous ownership, architecture and sensitive trust decisions with the main reasoner
or a suitable configured strong profile. No failed cheap attempt is required first.
Use `craft-engineering-foundations` for context-discipline and execution-optimization detail,
including model choice, bounded returns, evidence reuse and continuation. Recheck affected
sources after edits. Tiny or tightly coupled work usually needs one owner.

Write only the detail needed for execution:

- State the observable success conditions and explicit exclusions from the request.
- Describe the approach and any alternative whose trade-off could change that choice.
- Start the implementation sequence with inspecting branch/index/worktree and relevant existing
  changes, then establishing a safe boundary under consumer branching/workspace policy and
  repository protection. Preserve unrelated work; select a task branch/worktree when required
  by policy or isolation/concurrency needs. Planning-only scope describes this without changing
  Git state. Do not add repository hooks to apply this guidance.
- Order the remaining implementation steps around actual dependencies; name likely paths
  and owners.
- Attach verification to outcomes, including material rejection, failure and recovery cases.
  Separate structural validity from user-facing usefulness using the artifact's actual criteria.
- Select security/testing guidance for affected concerns, such as confidential-data egress,
  renderer escaping or provider failures; reuse current selections rather than loading every
  discipline. Carry the approach and useful checkpoint boundary into delivery.
- Identify assumptions, blockers and the decision needed to remove each blocker.

When parallel work is worthwhile and authorized, separate independent assignments by outcome
and owned paths, name their dependencies and integration owner, and choose isolated workspaces
for concurrent writers. Keep overlapping changes sequential. Plan coherent review/rollback
boundaries; commit strategy and frequency follow consumer policy and existing authorization,
including one final commit or no autonomous commits. Worker count does not determine commit
count. Record resulting commit IDs when commits are authorized and useful. Use the
available engineering Git/context references for worktree and handoff details.

For persisted data or public interfaces, account for old and new consumers during transition,
change ordering and the limits of recovery. Distinguish undoing a code edit from reversing an
external effect. Preserve durable rationale in `craft-delivery-write-adr` only when it needs
its own maintained record.

Keep the plan internal by default: use the conversation or an existing private task/checkpoint
store. Track scope, acceptance, decisions, completed/remaining units, checks and commit IDs in
one compact record. Use a requested file location when supplied; a checkout-local `.plan/`
requires verified exclusion from version control, or use storage outside the checkout.
Do not change shared ignore policy merely to store a plan. Internal notes are not repository
deliverables: never stage them or reference their paths, task IDs or checklists from shipped
code, tests, comments, docs or commit messages. Express necessary rationale in durable domain
terms. Only an explicit request to version a plan makes it a repository artifact; a requested
local path alone does not. Do not create per-step reports or duplicate code explanations.
If the request authorizes implementation, proceed with `craft-delivery-apply-change` once
its dependencies are understood. A planning-only request ends with a reviewable plan.
